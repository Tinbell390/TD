# ChatGPT・Claude共同開発：タワーディフェンスゲーム

## 1. プロジェクト概要

ChatGPTとClaudeが共同で開発する、HTML・CSS・JavaScriptのみで動作するタワーディフェンス（TD）ゲームのプロジェクト。

複数のステージと多様なゲームシステムを実装し、プレイヤーがさまざまな戦略を選択できるゲームを目指す。また、AI同士の協議・実装・レビュー・テストを通じて、共同開発の有効性を検証する。

## 2. 技術・実行環境

- 使用技術：HTML、CSS、JavaScript
- 実行環境：PC版Braveブラウザ
- ローカルサーバー：Python標準ライブラリの `http.server`
- ビルドツールやサーバーサイド処理は使用しない。
- 外部ライブラリを導入する場合は、事前に協議し、`specification.md` に記録する。

### 起動方法

プロジェクトのルートディレクトリで実行する。

```bash
python -m http.server 8000
```

Braveで `http://localhost:8000/` にアクセスする。

## 3. ゲーム開発方針

- ゲームジャンルはタワーディフェンスとする。
- 複数のステージを追加・管理できる構成にする。
- タワー、敵、マップ、強化要素などにバリエーションを持たせる。
- プレイヤーが複数の戦略を選択できるようにする。
- ゲームバランスとプレイの自由度を両立させる。
- 具体的なゲーム仕様は `specification.md` に定義する。
- 合意前の提案や未決事項を、確定仕様として実装しない。

## 4. ファイル・ディレクトリ構成

```text
TD-Game/
├── README.md
├── specification.md
├── discussion.md
├── Changes.md
├── logs.md
├── Marge.py
├── discussion/
│   └── YYYYMMDD_HHMMSS_ffffff.md
├── Changes/
│   └── YYYYMMDD_HHMMSS_ffffff.md
├── logs/
│   └── YYYYMMDD_HHMMSS_ffffff.md
├── index.html
├── style.css
├── js/
└── assets/
```

`js/` や `assets/` などのゲーム実装用構成は必要に応じて変更してよい。記録用ディレクトリと管理ファイルの役割は維持する。

### 管理ファイルの役割

| ファイル | 役割 | 更新方針 |
|---|---|---|
| `README.md` | 開発ルール・運用方法 | 協議のうえ更新 |
| `specification.md` | 合意済みのゲーム仕様 | 合意後に変更可 |
| `discussion.md` | 協議記録の集約先 | AIによる直接編集禁止 |
| `Changes.md` | 仕様変更履歴の集約先 | AIによる直接編集禁止 |
| `logs.md` | 作業ログの集約先 | AIによる直接編集禁止 |
| `Marge.py` | 追記記録を集約するツール | 承認なしに変更しない |

## 5. 記録ファイルの運用

### 5.1 基本方針

`discussion.md`、`Changes.md`、`logs.md` は集約先となるメインファイルであり、AIは直接編集してはならない。

各AIは記録を専用ディレクトリに新規Markdownファイルとして作成する。メインファイルへの反映は `Marge.py` を使用して行う。

| 記録種別 | 集約先 | 追記用ディレクトリ |
|---|---|---|
| 協議記録 | `discussion.md` | `discussion/` |
| 仕様変更履歴 | `Changes.md` | `Changes/` |
| 作業ログ | `logs.md` | `logs/` |

### 5.2 追記用ファイルのルール

- 記録ごとに新しいMarkdownファイルを作成する。
- 既存の追記用ファイルは編集・上書きしない。
- ファイル名は作成日時を基に一意にする。形式は `YYYYMMDD_HHMMSS_ffffff.md` を推奨する。
- 日時は日本時間（JST、UTC+09:00）を使用する。
- 記録には作成者、日時、種別、目的、内容を記載する。
- 協議記録では、提案・質問・合意・不採用・未決を区別する。
- 記録作成に失敗した場合、作成済みとして報告しない。

記録ファイルの例：

```markdown
---
record_id: discussion-20261009-204500-123456
created_at: 2026-10-09T20:45:00+09:00
author: ChatGPT
type: proposal
status: pending
---

## 内容

提案や協議内容を記載する。
```

`record_id` は記録ごとに一意とする。状態が変わった場合は既存記録を編集せず、新しい記録を作成して状態変更を残す。

### 5.3 マージの実行方法

まず、マージ対象を確認する。

```bash
python Marge.py --dry-run
```

問題がなければマージする。

```bash
python Marge.py
```

よく使うオプション：

```bash
python Marge.py --no-delete
python Marge.py --only discussion
python Marge.py --only Changes logs
```

- `--dry-run`：対象一覧を表示する。書き込み・削除は行わない。
- `--no-delete`：マージ後も追記用ファイルを残す。
- `--only`：指定した記録種別だけを処理する。

### 5.4 マージ時の安全規則

- マージ前に対象ファイルと件数を確認する。
- メインファイルが存在する場合は、書き換え前にバックアップする。
- マージ済み記録を二重に取り込まない。
- 書き込み後に内容を検証する。
- マージまたは検証に失敗した場合、追記用ファイルを削除しない。
- 削除は正常なマージと検証が完了した場合に限る。
- 不整合や競合が検出された場合は、独断で破棄・修正せず、人間の確認を求める。
- `Marge.py` の処理結果を確認し、Gitで変更差分をレビューする。

**注意：** `Marge.py` は記録の集約を補助するものであり、OSレベルの書き込み制限や同時実行ロックを提供するものではない。メインファイルへの直接編集を技術的に防ぐ必要がある場合は、Git差分チェックやアクセス権限も併用する。

## 6. 仕様管理ルール

- `specification.md` を合意済み仕様の正とする。
- AIは仕様変更を提案できるが、合意前に確定仕様として反映しない。
- 仕様変更を行う場合、変更理由と協議結果を記録する。
- 仕様書を変更したら、`Changes/` に変更履歴を作成する。
- 関連する協議は `discussion/` に記録する。
- 実装への影響、テスト結果、未解決事項は `logs/` に記録する。
- `Changes.md`、`discussion.md`、`logs.md` への反映は `Marge.py` を介して行う。

## 7. AIの作業ルール

### 7.1 作業開始前

作業開始時に、関連する次の資料を確認する。

1. `README.md`
2. `specification.md`
3. `discussion.md` および `discussion/` 内の関連記録
4. `Changes.md` および `Changes/` 内の関連記録
5. `logs.md` および `logs/` 内の直近・関連記録
6. 関連するソースコードとテスト

必要な情報が不足している場合は、推測で確定せず、質問または協議を行う。

### 7.2 実装・修正時

- 合意済み仕様に従って実装する。
- 変更範囲を必要最小限にする。
- 他のAIが作成したコードを、根拠なく削除・置換しない。
- 既存機能への影響を考慮する。
- 仕様変更が必要な場合は、実装前に協議する。
- 複数のAIが同じファイルを同時に編集しないよう、担当範囲やGitブランチを分ける。
- コードコメントは処理の意図や理由が分かりにくい箇所に記載し、コメントと実装を一致させる。
- 作業結果は `logs/` に新しい記録ファイルとして作成する。

### 7.3 作業完了時

- 仕様に沿っていることを確認する。
- 変更した機能と既存機能をテストする。
- Brave上での動作確認を行う。
- 実施したテストと結果を `logs/` に記録する。
- 未実施のテストを実施済みとして報告しない。
- 未解決の問題や既知の制約を明記する。

## 8. 共同開発フロー

1. ゲームのコンセプトや仕様案を `discussion/` に記録する。
2. ChatGPTとClaudeが仕様案を協議する。
3. 合意内容を `specification.md` に反映し、変更があれば `Changes/` に記録する。
4. 実装タスクと担当範囲を決める。
5. 担当AIが実装し、必要に応じて別のAIがレビューする。
6. ローカル環境で動作確認とテストを行う。
7. 作業内容と結果を `logs/` に記録する。
8. 必要なタイミングで `Marge.py --dry-run` を実行し、対象を確認する。
9. 問題がなければ `Marge.py` で記録を集約する。
10. Gitの差分を確認し、承認された変更を統合する。
11. 次のタスクに進む。

## 9. 判断の優先順位

判断が競合した場合は、次の順に確認する。

1. 本README.mdの開発ルール
2. 合意済みの `specification.md`
3. `discussion/` に記録された合意事項
4. 既存実装と関連する作業記録
5. 各AIの新しい提案

上位のルールを変更する必要がある場合は、変更そのものを協議し、合意と記録を残す。

## 10. 開発の基本原則

- 合意済み仕様を優先する。
- 不明点を独断で確定しない。
- 記録ファイルとメインファイルの役割を混同しない。
- 過去の記録を改変せず、変更を追跡可能にする。
- レビューは根拠と再現可能なテストに基づいて行う。
- 動作確認を通じて実装の正しさを検証する。
- ゲームの完成度と開発プロセスの改善を両立させる。
